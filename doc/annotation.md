# Описание разметки набора данных `energy_obj`

Подробное описание формата аннотаций, семантики классов и пайплайна разметки. Общая информация о датасете — в [dataset.md](dataset.md).

## Формат аннотаций

Датасет использует **YOLO-формат текстовых меток** (как в экспортах Label Studio и датасетах Ultralytics):

- Одна строка = один объект, строго 5 полей через пробел:
  `<class_id> <x_center> <y_center> <width> <height>`
- Все координаты — float в диапазоне [0, 1], нормализованы на ширину/высоту **всего изображения** (тайла ~10000×10000 px):
  - `x_center`, `y_center` — центр бокса;
  - `width`, `height` — размеры бокса.
- `class_id` — целое число, индекс класса из `classes.txt` (0..4). Дробные id (например `1.5`) считаются ошибкой валидации.
- Порядок строк не определён; переводы строк между объектами не допускаются.
- Файл без единой строки = изображение без аннотаций (см. «Пустые метки» ниже).

Пример (`labels/train/Mendeleevo-8-3.txt`):

```text
2 0.31355787602538265 0.07924389611644261 0.010473632155041024 0.009287937948809973
1 0.5554888980217811 0.25008266966423925 0.011165287108679735 0.011659326361263314
4 0.5476830778307576 0.2383245354524446 0.013339059820099445 0.010868863557120351
```

Боксы объектов маленькие: типичный опорный бокс — доли процента от тайла (на 10000 px ширины тайла `width = 0.01` ≈ 100 px).

### Соответствие «изображение ↔ метка»

- Метка лежит в `labels/<split>/` рядом со сплитом изображения, имя файла = stem изображения с расширением `.txt`: `images/train/X.jpg` ↔ `labels/train/X.txt`.
- Имя уникально в пределах всего датасета (плоская выкладка) — сборщик падает при коллизиях.

## Семантика классов

Порядок классов в `classes.txt` фиксирует YOLO id. Имена и состав — из конфигурации проекта Label Studio (`notes.json` в каждом экспорте):

| id | Имя | Что размечается |
|---|---|---|
| 0 | `substation` | Подстанция / комплектное распределительное устройство (объект в целом) |
| 1 | `supports 0,4` | Опора воздушной линии электропередачи класса 0,4 кВ |
| 2 | `supports 10` | Опора ВЛ класса 10 кВ |
| 3 | `supports 35` | Опора ВЛ класса 35 кВ |
| 4 | `transformer` | Трансформатор (отдельно стоящий, на опоре) |

Принципы разметки (по факту разметки в датасете):

- Объекты размечаются прямоугольными боксами по внешним границам видимого объекта.
- Одно изображение содержит от 1 до 48 объектов (медиана — 4, среднее — 5.7 бокса на тайл).
- Тип опоры определяется по контексту линии, к которой она относится; при сомнениях класс выбирался по напряжению ближайшей линии.
- Класс `substation` размечался как вся площадка подстанции одним боксом.

## Имена файлов и экспорты Label Studio

Label Studio называет файлы меток с хеш-префиксом: `<8-hex>-<stem>.txt` (например `deadbeef-Obvinsk-28-46.txt`). При сборке хеш снимается, метка переименовывается в `<stem>.txt`. Поддерживаются также URL-encoded имена (`%D0%...`) — они декодируются перед сопоставлением.

Каждый экспорт содержит:

```text
project-N-at-<дата>-<хеш>/
├── images/     # <stem>.jpg + рядом <stem>.jgw / <stem>.prj
├── labels/     # <хеш>-<stem>.txt
├── classes.txt # порядок классов
└── notes.json  # категории (id, name) + служебная информация
```

Сборщик требует, чтобы все смерженные проекты имели одинаковый набор классов (`notes.json`/`classes.txt`), иначе сборка падает.

## Пайплайн разметки

```text
исходные ортотайлы (с .jgw/.prj)
  → импорт в Label Studio
  → ручная разметка боксами по 5 классам
  → экспорт проекта в формате YOLO (zip)
  → распаковка в data/raw_part2/extracted
  → scripts/prepare_energy_dataset.py --merge   (мерж в датасет)
  → scripts/prune_unlabeled.py                  (не размеченное → в пул)
  ← пул data/energy_obj_unlabeled → доразметка → снова --merge
```

### Мерж

`prepare_energy_dataset.py --merge --source-root <export root>`:

1. Проверяет, что классы экспорта совпадают с классами датасета.
2. Проверяет отсутствие коллизий имён изображений с существующими.
3. Новые изображения распределяются по сплитам детерминированно (`--seed 42`, по умолчанию 70/15/15); уже лежащие в датасете изображения сплит не меняют.
4. Обновляет `metadata.json` (источники, счётчики, конфликты) и `README.md`.

### Дубликаты меток

Если на одно изображение претендуют несколько `.txt` (переэкспорт проекта), оставляется файл с **наибольшим числом строк-аннотаций**, остальные отбрасываются. Все случаи фиксируются в `metadata.json → resolved_label_conflicts` и в README датасета (на данный момент 5 конфликтов: 4 в Mal_kazan, 1 в zukai).

### Метки без изображения (unmatched)

Файл метки, для которого не нашлось изображения (по stem'у, после снятия хеша и URL-декодирования), **не переносится** в датасет. Список — в `metadata.json → unmatched_labels` (1 файл: `c47afd43-Alikino-15-25.txt` из energy2).

### Пустые метки

Изображение без файла метки получает **пустой `.txt`** (0 байт). Важно: пустая метка означает «объектов нет» и визуально неотличима от «разметка ещё не сделана» — именно поэтому после мержа raw_part2 (716 неразмеченных изображений) был выполнен прунинг.

### Прунинг и пул доразметки

`scripts/prune_unlabeled.py` переносит все изображения с пустыми метками в `data/energy_obj_unlabeled/` (плоские `images/`, `labels/`, `geo/` + `manifest.json` с указанием исходного сплита каждого тайла). Прунинг обновляет `metadata.json` и перегенерирует `README.md` датасета.

Обратный мерж пула: разметить изображения пула в Label Studio, экспортировать YOLO и выполнить `--merge --source-root <export>`. Имена тайлов сохраняются, поэтому после мержа повторный прунинг вернёт в пул только те, что остались без аннотаций.

## Контроль качества

Что проверяют скрипты сборки (жёстко, со stop-ошибкой):

- строго 5 колонок в каждой строке метки, `class_id` — целое число, известное из классов экспорта;
- уникальность stem'ов изображений внутри проекта и имён в плоской выкладке;
- идентичность набора классов во всех смерженных проектах и в датасете;
- наличие `images/` и хотя бы одного изображения в каждом проекте.

Что **не** проверяется автоматически (остаётся на разметчике и ревью):

- геометрическая корректность боксов (выход за границы тайла, нулевые/отрицательные размеры, пересечения дублирующих боксов одного объекта);
- семантическая правильность класса опоры;
- полнота разметки (непроставленные объекты).

Тесты: `tests/test_energy_dataset.py` (сборка, мерж, конфликты, прунинг, детерминизм сплитов).

## Известные особенности и ограничения

- **Дисбаланс классов:** `supports 10` — 3603 бокса (73%), `substation` — всего 7 аннотаций на 4 изображениях; в test-сплите `substation` отсутствует вовсе. Метрики по редким классам шумные.
- **Пустой test по substation** — при сравнении моделей по этому классу val-сплит информативнее.
- **716 тайлов ждут доразметки** (`data/energy_obj_unlabeled`), преимущественно Obvinsk, Konusyata, zukai, kusher — после разметки датасет вырастет примерно вдвое.
- **Часть тайлов без `.prj`** (340 из 864) — привязка есть только через `.jgw`; для картографического вывода проекцию нужно брать из соседних тайлов региона.
- Разметка велась разными разметчиками в 10 проектах Label Studio; единый гайд в виде кода отсутствует, поэтому для доразметки пула имеет смысл сверяться с уже размеченными тайлами того же региона.
