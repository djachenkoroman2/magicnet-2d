# Рекомендации по выбору конфигурации детекции для `energy_obj`

Рекомендации по обучению детектора на подготовленном датасете `data/energy_obj` (см. [dataset.md](dataset.md)). Составлено 2026-11-15 после проверки результатов прошлых прогонов и профиля датасета.

## Почему текущий конфиг не работает

Ранее действующий конфиг `configs/project/yolov3_d53_energy_obj_mmdet.toml` (MMDetection, YOLOv3-darknet53, вход 608px, обучение с нуля) по логам `log/yolov3_d53_energy_obj_mmdet_e2800_to_e3200` после ~2850 эпох дал **mAP@0.5 ≈ 0.0004** (2 TP / 111 FP / 298 FN) — фактически ноль. Конфиг, его логи и чекпойнты удалены при очистке проекта 2026-11-16 (см. чеклист ниже). Причины:

1. **Масштаб.** Изображения ~10000×10000 px; при ресайзе целого кадра в 608px типичный бокс (~0.02% площади кадра) превращается в ~8 px — ниже разрешения детектора.
2. **Обучение с нуля** (`disable_pretrained = true`) на всего 864 изображениях.
3. **Дисбаланс классов:** `substation` — 7 боксов, `transformer` — 104, `supports 35` — 155 при 3603 у `supports 10`.

Профиль датасета (по 4910 боксам): медианная относительная площадь бокса 0.0002, 66% боксов ≤ 0.0004, 76% ≤ 0.001. Боксы мелкие относительно кадра — это главное свойство задачи.

## Ключевая рекомендация: обучать на тайлах

Не менять модель «в лоб», а менять масштаб подачи данных: резать кадры на тайлы (например, 1280×1280 px, перекрытие 15–20%). Один 10k×10k кадр даёт ~60–100 тайлов.

- Объекты становятся 30–300 px на тайле — в рабочей зоне детектора.
- Эффективный объём датасета вырастает до ~40–60k изображений.
- Ликов нет, если тайл наследует сплит родительского кадра (текущие сплиты image-level — наследование прямое).
- В набор стоит включить 10–20% пустых тайлов как фон, иначе рост ложных срабатываний на фоне.

Цена вопроса: шаг препроцессинга и аккуратный мердж предсказаний на инференсе (скользящее окно + NMS по тайлам). Geo-привязка (`.jgw` в `geo/<split>/`) сохранена — агрегированные предсказания можно переводить обратно в геокоординаты.

## Как выбрать размер тайла

Тайлинг **не масштабирует** изображение — боксы сохраняют нативный размер в пикселях. Размер тайла влияет только на то, насколько тайл сожмётся до входного разрешения модели (а вот это объекты уже уменьшает), плюс на контекст, объём данных и время эпохи. Выводится из трёх ограничений.

### Шаг 1. Нативные размеры объектов (по датасету)

Линейный размер объекта `sqrt(width × height)` в пикселях при ширине тайла ~10000 px:

| класс | p5 | p25 | медиана |
|---|---:|---:|---:|
| supports 0,4 | 49 | 71 | 99 |
| supports 10 | 68 | 106 | 165 |
| supports 35 | 65 | 97 | 155 |
| transformer | 76 | 99 | 122 |
| substation | 33* | 55 | 1233 |

\* у substation p5 и медиана сильно расходятся — всего 7 объектов, не показательно. Типичный мелкий объект — 50–80 px, медианный — 100–165 px.

### Шаг 2. Нижняя граница: объекты выживают при сжатии до входа модели

Если вход модели S (например 1280), тайл T, объект B px, то на входе объект станет `B × S/T`. Детектор уверенно работает с объектами ≥ ~16–20 px (лучше 30+). Для самых мелких (~50 px):

```
T ≤ B_small × S / min_px  →  T ≤ 50 × 1280 / 20 ≈ 3200
```

| тайл T | сжатие до 1280 | объект 50px на входе |
|---:|---:|---:|
| 1024 | ×1.25 (апскейл) | 62px |
| 1280 | ×1.0 | 50px |
| 1536 | ×0.83 | 42px |
| 2048 | ×0.63 | 31px |
| 2560 | ×0.5 | 25px |

Вплоть до 2560 всё ещё терпимо — размер объекта здесь **не биндинг-констрейнт**, выбор делается по другим критериям.

### Шаг 3. Верхняя граница и практика

- **Контекст:** тайл должен быть заметно больше типичного объекта, иначе в кадре окажется один обрезанный объект. Ориентир: T ≥ 5–10× медианы → от ~800–1600 px.
- **Объём данных/время эпохи:** при T=1280 и шаге ~1024 (перекрытие 20%) один 10k-кадр даёт ~90–100 чипов (~80k на датасет); шаг 1280 без перекрытия — ~49 чипов/кадр, вдвое быстрее.
- **Правило «без ресайза»:** самый чёткий вариант — тайл равен входу модели (1280 → imgsz 1280), пересэмплирования нет вовсе.
- **Перекрытие 15–25%**, чтобы объекты на границах не резались; боксы на краях обрезаются по границе тайла (стандартно).

### Рекомендация и проверка

Для `energy_obj`: **T = 1280, шаг 1024 (20%), вход модели 1280** — объекты остаются 50–165 px, ноль ресайза. Если эпоха слишком долгая: шаг 1152 (~10%) или T=1024 (чипов без боксов будет больше).

Проверка выбора (~15 минут):

1. Отрендерить 5–10 худших тайлов (боксы ~50 px) с наложенными боксами — объекты различимы?
2. Два коротких обучения (10–15 эпох) на кандидатах (например, 1280 vs 2048), сравнить val mAP@0.5 — разница видна сразу.
3. Отдельно проверить визуально `substation`: с медианой 1233 px объект может занимать целый тайл 1280 — не режутся ли эти 7 объектов границами.

## Выбор конфигурации

### Вариант 1 — MMDetection (запускается без установки пакетов)

Среда venv уже содержит mmdet 3.3.0 / mmcv 2.1.0 / torch 2.1.0+cu121. Работает существующий пайплайн `scripts/train.py` и кастомные метрики (`energy/mAP@0.5`, per-class AP).

- Модель: **RT-DETR r50** (`mmdet::rtdetr/rtdetr_r50vd_...`) либо надёжные **Faster R-CNN r50 FPN** / **Cascade R-CNN r50 FPN** — хорошо работают на мелких объектах, быстро сходятся на малом датасете.
- **Обязательно COCO-pretrained** (`load_from`, классификационный слой переинициализируется автоматически).
- Вход 1024–1408 px, batch 8–16 — помещается в RTX 4090 24GB.

### Вариант 2 — Ultralytics YOLO (проще, но нужна установка)

В venv пакет `ultralytics` отсутствует (веса `yolov8n.pt`/`yolo26n.pt` в корне репозитория есть, но в окружение не установлены).

```bash
uv pip install ultralytics
```

- Модель: **YOLOv8s/m**, `imgsz=1280`, pretrained, mosaic + флипы, ~100–150 эпох.
- Инференс тайлами — через SAHI (скользящее окно + мердж).
- Пайплайн `scripts/yolo_train.py` и конфиги `configs/yolo/*.yaml` уже есть в репозитории.

### С чего начать

Вариант 1: всё необходимое уже в venv, метрики репозитория продолжают работать. Вариант 2 — разумный следующий шаг для сравнения качества.

## Дополнительные меры (независимо от варианта)

1. **Редкие классы.** `substation` (7 боксов) почти не выучится; `transformer` и `supports 35` — пограничные. Варианты: oversampling изображений с редкими классами, copy-paste-аугментация, временное слияние классов в один `support` с последующим дроблением после доразметки.
2. **Пул доразметки.** 717 неразмеченных изображений в `data/energy_obj_unlabeled` — главный резерв роста качества (особенно для редких классов).
3. **Инференс.** Только скользящим окном по тайлам с мерджем; прямой прогон целого 10k×10k кадра бесполезен (см. диагноз выше).
4. **Валидация.** Сплиты наследуются от кадров; отчётность — по метрикам репозитория для mmdet, встроенной валидацией для ultralytics.
